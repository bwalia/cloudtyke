Azure landing zones · the reference hierarchy

Management groups and subscriptions

Azure landing zones organise an estate as a tree. Management groups hold the rules. Subscriptions hold the resources. A rule set on a group reaches every subscription below it.

Figure 1

The Azure landing zones hierarchy

Identity sits across the top: one Microsoft Entra ID tenant, Privileged Identity Management and role-based access. Below it, Contoso is the organisation's own top group. Platform groups hold shared services. Landing zones hold the apps. Two more groups handle the start and end of a subscription's life: Sandbox and Decommissioned.

Scroll the drawing sideways to see it all. Details appear below it.

Figure 2

One request, every rule above it

When someone builds a resource, Azure Policy collects every assignment from the subscription and from each group above it. If any of them says Deny, the request fails with RequestDisallowedByPolicy. Pick a request to see which rule decides.

Policy effects in short: Deny blocks the request. Audit lets it through and marks it non-compliant. DeployIfNotExists and Modify add or fix settings, using a managed identity.

Practise in CloudTyke

Policy assignments at management group scope are enforced on every write. Run bash landing-zone-stadium/scripts/up.sh, then try to create a public IP in sub-events: the initiative in terraform/safety-code.tf denies it. Built-in definitions are not seeded, and DeployIfNotExists never deploys.

In the stadium

The tenant root group is the land. Platform is the stadium shell, built once. Landing zones is the pitch, where events happen. Sandbox is the training ground. The policy that flows down is the stadium's safety code: Chapter 3, The safety code.
